# West Coast Construction Group - Redirect Configuration

These redirects are applied in **WordPress**, not in the GitPress HTML fragments.
Fragments are body partials with no server or `.htaccess` control, so the 301 is
configured in the WordPress redirect layer (Yoast Premium Redirects, the Redirection
plugin, or the server config), then verified against the live site.

## Required 301 (spec section 4)

| From | To | Type |
|------|----|----|
| `/services/emergency-services/` | `/services/emergency/` | 301 (permanent) |

### Notes
- This is the emergency **parent** URL change. The old page lived at
  `/services/emergency-services/`; the rebuilt hub lives at `/services/emergency/`.
- All emergency child pages launch under the new parent
  (`/services/emergency/<slug>/`). Do **not** publish the child pages while the
  parent still resolves at `/services/emergency-services/` (spec section 4).
- Preserve the original page ID / SEO history where possible by converting the
  existing emergency page in place rather than deleting and recreating it
  (see GITPRESS_WEBSITE_STRUCTURE.md section 6, in-place conversion).

## Launch verification (spec section 18)
- `curl -sI https://wccgrp.com/services/emergency-services/` returns a single
  `301` to `https://wccgrp.com/services/emergency/` (no redirect chain).
- `https://wccgrp.com/services/emergency/` returns `200`.
- No other page 301s through the old emergency URL.

## Internal links already point to the new URL
Every internal link generated by `build.py` targets `/services/emergency/` and
`/services/emergency/<slug>/`. There are no internal links to
`/services/emergency-services/` anywhere in the fragments, so the redirect only
needs to catch external inbound links and search-engine history.
